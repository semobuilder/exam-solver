# 제한된 시험 환경 실전 운영

이 문서는 준비 전략이며 공식 사양이나 채점표가 아니다. 현재 안내·참가자의 실제 경험·확인한 도구 기능을 구분한다. 1,000자 입력과 첨부 5개는 해당 통로에서 확인될 때 적용한다. 후속 AI 불가 단계의 문항을 대신 답하지 않는다.

## 짧은 프롬프트와 작업 상태

- 목적은 제한 우회가 아니라 각 요청을 독립적으로 이해 가능한 작은 작업으로 만드는 것이다. 참가자가 보낼 지시는 원칙적으로 800자 이내로 만들고, 확인된 상한보다 여유를 둔다. 코드 블록 안의 내용만 복사하게 한다. 문장을 나눠 보내며 이전 조각을 기억한다고 가정하지 않는다.
- 파일을 읽을 수 있으면 현재 작업의 근거 파일·절·함수를 지정해 실제로 읽는다. 경로만 말한 것은 읽기 증거가 아니다. 첨부만 가능한 통로에서는 현재 상태 요약+해당 규칙 원문+현재 데이터/코드+실패 사례 중 필요한 것만 최대 5개 이내로 요청한다. 모든 파일을 매 턴 첨부하지 않는다.
- 첨부가 다음 턴에도 유지되는지 확인되지 않으면 필요한 근거를 이번 턴에 다시 포함한다. 읽을 수 없는 파일은 읽었다고 주장하지 않는다. 파일의 토큰·용량 한도도 지킨다.
- 과제 지정 Handoff/작업 기록에 상태를 통합한다. 지정이 없으면 `WORKLOG.md` 하나를 사용한다. 필수 산출물과 원문을 기록 파일로 대체하지 않는다.
- 상태 기록 최소 항목: 현재 버전, 목표·제출물, R1 등 규칙 ID와 출처·범위, 미확인 조건, 구현 위치·진행 상태, 마지막 실행 명령·관측 결과, 실패·미검증, 다음 행동. 원본 수치·단위·예외와 출처를 보존하고 변경된 규칙을 표시한다.
- 문맥 단절·세션 전환 후 최신 파일과 상태를 재확인한다. 오래된 대화 요약과 현재 코드가 다르면 차이를 조사한다. 전체 재구현하지 않는다.

### 단계별 요청 템플릿

아래는 참가자용 짧은 요청 예시다. 스킬이 이미 적용되면 참가자가 순서대로 입력할 필요 없이 AI가 내부 작업 순서로 사용한다. 대괄호는 실제 경로·조건·기록으로 채우고, 지시문 총 길이가 확인된 제한 안인지 확인한다.

```text
[요구사항]
과제 안내와 [자료]를 실제로 읽고 목표·필수 산출물·제약을 정리해. 확인/미확인/가정을 구분하고 규칙에 R번호와 출처를 붙여. 담당자별 핵심 질문 1~3개를 대상 표시와 함께 복사용으로 출력해. 이전 첨부나 대화가 보이지 않으면 필요한 근거를 요청해. 미확인 규칙에 의존하지 않는 준비만 진행하고 상태를 [작업기록]에 갱신해.
```

```text
[알고리즘]
[작업기록]의 최신 확정 규칙과 [입력 명세]를 읽어. 목적함수·필수 제약·자원 상한 유무·불가능한 입력 처리를 명시해. 제약을 지키는 기준해와 개선 방법을 비교하고 선택 이유를 적어. 입력 크기를 정의해 시간·공간 복잡도를 설명해. 작은 독립 정답 사례와 실패 반례를 먼저 정해. 휴리스틱의 최적성은 보장하지 마.
```

```text
[구현]
[작업기록]과 [대상 파일]의 현재 상태를 읽고 다음 미완료 필수 기능 하나를 구현해. 확정 규칙과 인터페이스를 지키고 임의 제약·새 기능을 추가하지 마. 실제 입력→처리→출력까지 실행해 결과를 확인해. 변경 위치·실행 명령·결과·미검증·다음 행동을 기록하고 다음 독립 작업으로 이어가.
```

```text
[디버깅]
현상:[오류]. 재현:[명령/입력]. 기대:[근거 있는 예상값]. 관측:[실제값/로그]. 최신 규칙·관련 코드로 재현하고 플랫폼/앱 오류를 구분해. 원인을 좁혀 최소 수정한 뒤 실패 사례와 영향받는 정상 흐름을 재검증해. 기대값을 현재 출력에 맞춰 바꾸지 마. 수정·관측 결과와 남은 문제를 [작업기록]에 갱신해.
```

```text
[복구]
새로 만들지 말고 [작업기록]과 현재 파일·프로세스부터 확인해. 확정 규칙·완료 기능·마지막 검증·미확인 사항을 복원해. 파일 보존이나 검증 통과를 추정하지 마. 서버 중복 실행을 피하고 남은 시간 [분]에 맞춰 다음 필수 작업부터 재개해. 읽을 수 없는 근거는 필요한 것만 요청해.
```

## 담당자 질문: 사례→갈림길→적용 범위→기대 결과

발견한 실제 사례 하나와 결과가 달라지는 선택을 제시한다. “다른 처리 기준이 있으면 알려주세요”를 붙여 유도된 양자택일을 피한다. 사업 목적·담당 범위가 불명확하면 먼저 확인한다.

| 우선순위 | 확인할 사항 | 범용 질문 형태 |
|---|---|---|
| 1 | 목적·완료 | 이 결과로 어떤 결정을 하나요? 필수 완료 기준은 무엇인가요? |
| 2 | 강제 제약·상한 없음 | 자원 수는 명시된 상한이 있나요, 제한 없이 늘릴 수 있나요? |
| 3 | 단위·시간·경계 | 이 값은 분/초 중 무엇인가요? 기준 시각과 같으면 포함인가요? |
| 4 | 예외·충돌 | 이 중복/누락 사례는 제외·보류 중 어느 처리인가요? 다른 규칙도 있나요? |
| 5 | 결과 확인 | 이 작은 입력에서 [예상 출력]이 업무상 맞나요? |

확인 답변을 R번호로 기록해 계획·코드·검증 사례에 연결한다. “현실적으로 보통 그렇다”는 가정으로 자원 제한, 우선순위, 휴식시간 등을 추가하지 않는다. 답변 충돌은 담당자·적용 기간·범위 차이를 먼저 확인한다.

질문의 종료 기준은 대화 횟수가 아니라 필수 결과·정확성·설계를 바꾸는 갈림길의 해소다. 매 답변에서 `새로 확정한 규칙 / 바뀌는 구현·검증 / 아직 남은 핵심 질문`만 갱신한다. 새로운 정보가 없는 반복 질의는 사례로 한 번 좁히고, 답을 얻지 못한 부분은 미확정으로 남긴 채 독립 작업을 진행한다. 자료만으로 명확한 조건은 재질문하지 않는다.

## 180분 운영 예시

아래는 작업 단계 180분을 온전히 쓸 수 있을 때의 권장 예시다. 현재 남은 시간과 전체 시험 종료 시각, 후속 문항·준비 대기 시간을 함께 확인해 조정한다. 장애 대기는 자동 연장으로 간주하지 않는다.

연장 공지와 실제 타이머·종료 화면이 다르면 적용 여부를 문의하고, 확인 전에는 더 이른 종료에 맞춰 저장·제출 준비를 한다. 스킬·템플릿 설치와 요구사항 정리는 필수 흐름 구현을 지연시키지 않는 범위에서 끝낸다.

| 경과 | 목표와 점검 |
|---|---|
| 0~15분 | 안내·입력·산출물·도구 기능 확인, 담당자 질문과 상태 기록 시작 |
| 15~30분 | 핵심 규칙 확정, 작은 예상 정답, 기준해·인터페이스·환경 파일 최소 구조 |
| 30~80분 | 실제 입력부터 필수 출력까지 하나의 전체 흐름, 실행·파일 열기 확인 |
| 80~115분 | 남은 필수 기능과 필요한 알고리즘 개선, 기준해 대비 지표·제약 검사 |
| 115~145분 | 반례·경계·독립 대사·실패 복구, 최종 출력 재검증 |
| 145~160분 | 실행·환경 빌드·필수 문서 대조, 실제 구현 이해 확인 |
| 160~180분 | 저장·미리보기·제출 여유. 안내가 권장하는 시점에 제출 시작 |

80분에 전체 흐름이 없으면 장식·선택 기능을 중단한다. 145분 이후에는 필수 정확성·실행·제출을 막는 문제만 수정하고 관련 재검증을 한다. 필수 성능·최적성은 시간 부족 때문에 선택 기능으로 바꾸지 않는다. 문서는 마지막에 몰아서 쓰지 않고 각 점검 시 갱신한다.

### 도메인별 검증 초점

빈출 예측이 아니라 서로 다른 모의 과제를 연습하기 위한 분류다. 실제 문제에 필요한 것만 적용한다.

| 연습 유형 | 먼저 확인 | 기준해·검증 |
|---|---|---|
| 물류·경로 | 목표 비용, 방향·연결성, 용량·차량 상한, 시간창, 불가능 처리 | 작은 완전탐색 등 독립 정답과 비교, 제약 위반 수·비용·실행시간 |
| 공정 스케줄링 | 선후관계, 설비 적합성, 용량, 전환시간, 납기, 시간 단위 | 단순 가능 스케줄, 선후·자원 중첩 검사, 작은 정확해·목적값 대조 |
| 데이터 파이프라인 | 키·중복·최신 기준, 결측·지연, 스키마, 재처리 범위 | 전후 건수 대사, 재처리 중복 방지 요구 확인, 오류 격리·실패 후 복구 |

### 웹앱·빌드 점검

제공 환경에서 서버는 안내에 맞춰 `0.0.0.0`과 실제 포트로 실행하고 내부 Browser에서 경로·버튼·입력·내보내기를 확인한다. 서버 탭을 유지하고 본인 프로세스만 관리한다. 미리보기 응답 대기와 플랫폼 장애를 구분한다.

Dockerfile이 필수면 시작·의존성·포트·실행 명령을 실제 앱과 맞춘다. Docker 실행 권한이 있으면 빌드·실행을 확인하고, 없으면 일반 실행으로 확인한 범위와 컨테이너 실행 미검증을 구분해 기록한다. Docker 설치나 권한 우회를 시도하지 않는다. 환경 파일이 존재한다는 것만으로 빌드 성공을 주장하지 않는다.

## 구현·비판·문서 역할

한 세션에서 구현 후 잠깐 역할을 바꿔 R번호별 누락, 실제 실행, 반례, 문서 불일치를 검토한다. 자기 검토는 독립 검증을 대신하지 않는다. 작은 정답 계산·불변식·실제 재실행으로 확인한다.

다중 세션은 선택 사항이며 고득점의 근거가 아니다. 지원과 참가자 요청이 있을 때만 구현 세션에 쓰기 권한을 집중하고, 검토는 관측된 근거를 반환하게 한다. 문서 갱신도 구현 파일과 동시에 덮어쓰지 않는다. 세션마다 같은 최신 규칙·버전을 읽고 실제 차이를 통합한다. 토큰·RAM·CPU·대기 비용이 더 크면 한 세션으로 돌아온다.

## Handoff와 AI 없는 설명 준비

과제의 지정 파일과 형식이 우선이며 아래 항목을 기존 문서에 통합한다.

1. **문제·규칙:** 사용자 목표, R번호·출처·확정/미확인, 완료·부분·미완료 상태.
2. **실행:** 입력·환경·실행/검증 명령, 출력 위치, 재현 가능한 작은 예시.
3. **구조:** 입력→검증→핵심 로직→출력, 실제 파일·함수 연결. 핵심 선택마다 이유·해당 코드·실패 시 응답과 데이터 보호 동작·검증 사례를 연결한다. 보호 동작이 없거나 미검증이면 그대로 밝힌다.
4. **알고리즘:** 선택 이유·버린 대안, 변수 n/m 등의 정의, 최악/평균 조건에 맞는 시간·공간 복잡도와 병목, 정확해/근사/휴리스틱의 보장 범위.
5. **검증:** 사례·예상·실제·판정, 실패 원인·수정·재검증, 명령·코드 위치. 관측한 사실만 기재.
6. **한계·복구:** 남은 오류·미검증, 재시작 방법, 다음 개선과 비용.

설명을 준비할 때 실제 최종 코드에서 주요 비용을 계산한다. 라이브러리 호출 하나나 알고리즘 이름만 보고 복잡도를 단정하지 않는다. 전처리·반복·정렬·외부 호출·출력 비용과 메모리도 포함한다. 실행시간 측정과 이론 복잡도는 구분한다.

5분 답변 연습은 문항별 30초 요구 파악, 30초 근거·구조 구상, 3분 작성, 1분 사실 대조를 기본으로 타이핑 속도에 맞춰 조정한다. 질문이 요구한 것부터 답하고 관련 없는 설명을 채우지 않는다.

기억 순서는 **결론→실제 위치·동작→선택 이유→검증 증거→한계**다. 모든 답에 다섯 항목을 억지로 넣지 않는다. 예컨대 복잡도 질문에는 변수 정의·지배 연산·증가 양상·병목을 우선 답한다. 질문의 전제가 구현과 다르면 실제 차이를 먼저 밝힌다. 수치·보장·테스트 횟수를 기억이 안 난다고 지어내지 않는다.

핵심 기능 완성 때 AI 접근이 가능한 작업 단계에서만 30초 요약과 이해 확인을 연습한다. 예: “입력 검증은 어느 함수에서 하고, 실패하면 어떤 응답을 내며, 기존 결과가 어떻게 되는지 어떤 테스트로 확인했나요?” 참가자의 답을 듣고 틀린 부분만 피드백한다. 실제 후속 서술형 문항을 가져와 AI로 답하는 흐름을 만들지 않는다.
